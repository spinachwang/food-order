# ADR 0002 — 主 Agent 路由采用双层策略（规则优先 + LLM 兜底）

- **状态**：Accepted
- **日期**：2026-09-02
- **决策者**：项目负责人
- **关联 spec**：[F002](../features/F002-main-agent-router.md)、[F003](../features/F003-cuisine-expert-contract.md)、[F004](../features/F004-langgraph-workflow.md)

## 背景

F002 主 Agent 需要把用户的一句自然语言（"今天想吃辣的" / "随便" / "想吃点暖胃的"）
映射到 1–3 个菜系专家。纯 LLM 路由方案的问题是：

- **成本**：每次点单都要多付一次 LLM 调用，而 80% 的输入是"想吃辣的"这类关键词明确的消息
- **延迟**：LLM 往返 1–3s，用户点开页面到看到"正在问川菜专家"之间是纯等待
- **不可解释**：LLM 偶发漂移，`routing_reason` 质量不稳定

同时纯规则方案又覆盖不了"灰色地带"（"想吃点暖胃的" / "有点没胃口"）。

实现期还需就四个具体口径给出决议：模糊抽样的确定性、忌口硬拦的范围、
规则关键词的最小长度、以及本 feature 是否引入 `langgraph` 依赖。

## 决策

### 1. 双层路由：规则优先短路，LLM 只做兜底

第一层是纯内存的关键词规则引擎，命中即短路返回，**完全不调用 LLM**；
只有真正未命中（或互斥意图同时命中）才降级到第二层 LLM。

规则层按**意图标签（tag）分区**而非线性合并，且分两级优先级：
显式点名菜系（"想吃川菜"）> 口味修饰（"想吃辣的"）。
互斥标签（`spicy` × `light`，如"清淡的辣菜"）同时命中时**不做武断合并**，直接降级给 LLM。

理由：线性「命中即合并 + 截断」会产出自相矛盾的结果——
`"日料，清淡的"` 会因表序让 `japanese` 被粤苏浙挤掉，
`"想吃清淡的辣菜"` 会把川湘塞给想吃清淡的用户。

**时间预算因此分层**：规则/模糊层 < 100ms，LLM 兜底层 < 5s（超时降级）。
F002 原先写的「1 秒内完成路由决策」对第二层物理上不可达
（MiniMax 单次往返就 >1s），若硬套 1s 超时则第二层等于永久失效。

### 2. 模糊路由用加权随机抽样，`Random` 实例参数注入

"随便 / 都行 / 无所谓"走 `cuisine_weights` 的**加权随机抽样**（无放回，n ∈ {2,3}），
而非确定性 top-N 排序。

理由：这是一个午餐决策应用，"给我个不一样的答案"就是核心价值。
确定性 top-N 会让同一用户每次说"随便"都拿到完全相同的菜系组合
（默认权重全 0.5 时永远是 `[sichuan, cantonese]`），产品上不可接受。

为保证可测性，`random.Random` 实例通过关键字参数注入
（`route_cuisines(state, *, rng=None)`），测试传固定 seed 后行为完全确定，CI 不 flaky。

### 3. 忌口硬拦表严格取字面「100% 冲突」

`HARD_ALLERGY_CONFLICTS` 只收 3 个菜系：

| cuisine_id | 冲突过敏原 | 依据 |
|---|---|---|
| `fujian` | `shellfish`, `fish` | 「几乎无菜可吃」 |
| `western_fastfood` | `fried_food` | 「默认含」 |
| `sichuan` | `peanut` | F002 §2 点名的例子 |

理由：路由层是**粗筛**，粒度是整个菜系；一刀切掉整条菜系的代价很高。
粤菜蚝油、西餐奶制品、苏菜蟹粉这类属「部分菜品含」，
放到各菜系专家 prompt 的「过敏原注意」做**菜品级**规避即可（F003 §4 已有该段）。
若把「常见/常用」也纳入硬拦，一个 `shellfish` 过敏用户会一次损失 4 个菜系，
很容易触发 `ALL_CUISINES_FILTERED` 无菜可推。

### 4. 规则关键词强制 ≥2 字

F002 §3.3 初稿的 `"快"` / `"饱"` 单字关键词在子串匹配下误命中率过高：
「我**快**到了」「我吃**饱**了」「吃得有点**快**」都会被判成快餐意图。
改用 `快餐 / 简餐 / 吃快 / 快点吃 / 吃饱 / 饱腹 / 扛饿`，并加一条单测锁死该约束防回归。

### 5. F002 不引入 `langgraph` 依赖

本 feature 只交付一个 LangGraph-node **形状**的纯 async 函数
（`route_cuisines(state) -> RouterOutput`，即 `state -> 部分状态`），
与 Phase 1 已落地的 `BaseCuisineExpert.run(state) -> dict` 同构。

理由：真正的组图、`Send` 动态分发、`MemorySaver` checkpoint 都归 F004。
把依赖推迟到实际组图时引入，可让 F002 的单测完全脱离图运行时，跑得快且稳。

## 后果

- 常见输入零 LLM 成本、路由延迟从 ~1.5s 降到 <10ms；`routing_reason` 在规则层是静态文案，稳定可预期。
- 代价是规则表需要人工维护。新增菜系 / 新增说法要同步改 `routing/rules.py` 与 F002 §3.3。
- 规则表的关键词是产品口径的一部分，改动需要过 spec review，不能只改代码。
- 忌口硬拦表刻意保守：**过敏安全的最终防线在菜系专家与 F040 总结 Agent**，不在路由层。
  若 M2 出现「推荐了用户过敏的菜」的真实反馈，应优先加强 F040 的二次校验，而不是无脚本地扩大本表。
- `AgentState.cuisine_results` 的 `list` vs `dict` 不一致仍未收口，留给 F004 决议（代码中已标 `TODO(F004)`）。

## 备选方案

- **纯 LLM 路由**：实现最简、覆盖最广，但每次点单多付一次调用、延迟高、`routing_reason` 不稳定。已否。
- **纯规则路由**：零成本零延迟，但覆盖不了"暖胃 / 没胃口"这类灰色地带，用户会撞到 `NO_CUISINE_MATCHED` 兜底。已否。
- **规则 + 向量相似度检索**（把菜系描述向量化，用户消息取 top-k）：无需 LLM 也能处理灰色地带，
  但要引入 embedding 模型与向量库，M1 阶段过重。**M2 可重新评估**作为第二层的替代。
- **确定性 top-N 模糊路由**：更简单、更好测，但重复"随便"结果恒定，产品体验差。已否（见决策 2）。
